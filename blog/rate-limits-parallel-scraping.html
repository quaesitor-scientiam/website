Four browsers, one rate limit: what broke when I scraped in parallel

November 19, 2026 · Data Automation

One of my clients sells parts online. Their supplier publishes vehicle fitment data (which part fits which year, make and model) only inside a logged-in dealer portal. There is no API for it. So, with the client's dealer account and their authorization, I automated the portal: search a part number, open the detail view, read the fitment table, repeat for tens of thousands of parts.

One browser was too slow, so I ran four. That is where the trouble started.

The failure

On one run all four sessions received HTTP 429 ("too many requests") within about eleven seconds of each other. Each session did the sensible thing in isolation: wait, then retry. But they retried independently, and four uncoordinated retry loops did nothing to calm things down.

Then it got worse. One session degraded and restarted itself. Restarting means logging in again, and the login page was being throttled too. The login failed, the code concluded the session was dead, and it abandoned the whole brand it was working on, along with that brand's progress. The other three sessions could not log back in either.

Nothing was actually broken. The site was telling me to slow down, and my code was treating that as a crash.

Fix 1: when one session is told to wait, all of them wait

The four sessions now share one small piece of state: a "paused until" time. The moment any session confirms a 429, it pushes that time forward. Every session checks it before starting its next part and sleeps until it passes.

The detail that matters is when the signal goes out. My first version signalled after the session had recovered, minutes later, by which time the others had already piled on. Signalling at detection means the whole fleet backs off before the storm forms. Repeated 429s keep extending the window, so a stubborn limit produces a longer shared pause instead of four overlapping retry loops.

Fix 2: a throttled login is not a dead session

Logging in after a restart used to get one attempt with a 90-second timeout. Under throttling that is nowhere near enough. Login now retries on the same backoff schedule as everything else: start at 60 seconds, double each time, cap at ten minutes. Only when every attempt fails does the code give up on the session.

Fix 3: defer the part, keep the batch

If a part still fails after its session has been rebuilt, it goes onto a retry list and the run moves on. When the main pass finishes, the retry list is processed one part at a time, with the other three sessions idle. Parts that fail under concurrent load usually succeed when the site is only handling one request from me.

This turned the worst outcome from "lose the brand" into "one part is handled later".

Pacing so the limit is rarely reached

Backoff is the safety net. The better result is not tripping the limit at all. The settings I ended up with:

  • At least 12 seconds between parts in each session, plus a random 0 to 12 seconds so the four sessions do not fall into step.
  • A 90-second pause after every 40 parts, taken before the limit is reached.
  • A 30-second stagger at startup, so four logins do not arrive at once.
  • An extra 45 seconds of quiet after a 429 clears.

Each of these makes the run slower on paper. In practice the run finishes sooner, because it no longer spends hours recovering.

Keeping it alive for days

A full pass takes days, and over that time the browser driver itself dies about once a day. A small watchdog script checks every 15 seconds that the driver and the scraper are both running, and restarts whichever is missing. The scraper records which brand is in progress, so a restart resumes there.

One lesson came from a run that vanished just after midnight: start the watchdog from the operating system's task scheduler, not from a terminal. A process launched from a terminal session is a child of that session and disappears when the session ends, with no error anywhere.

What I would tell someone starting this

  • Treat a 429 as an instruction, not a fault. Slow down in a coordinated way.
  • Assume every page can be throttled, including login.
  • Make the unit of failure as small as possible. Losing one part is fine. Losing a batch is not.
  • Only automate a portal with the account owner's permission, and at a pace the site can comfortably serve.
